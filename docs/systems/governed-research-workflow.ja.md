<header class="component-header"><p class="component-kind">System</p><h1>Governed Research Workflow</h1><p>Study を、研究アイデアとデザインから実行・結果、原稿、改訂、アーカイブまで整理します。</p></header>

<section class="component-section component-summary system-summary"><p>研究計画書、実行、結果、原稿、改訂の記録を長く保持する必要がある時に使う System です。これらの資料を Study 内に置き、重要な決定がどこから来たかを残します。</p><div class="release-stamp"><span>現在の公開 Release</span><strong><a href="https://github.com/chenhaoran2068/governed-research-workflow/releases/tag/v1.18.0">v1.18.0</a></strong></div></section>

<section class="component-section" aria-labelledby="study-status-title"><div class="section-header"><div><p class="section-context">v1.18 の追加</p><h2 id="study-status-title">Study の現在地を確認する</h2></div><p><code>00_state/study_status_snapshot.json</code> に、短く確認可能な現在状態を残します。</p></div><div class="boundary-grid"><div><h3>まず稼働状態を記録する</h3><p><code>queued</code> は開始待ち、<code>active</code> は進行中、<code>paused</code> は再開可能な一時保留、<code>stopped</code> は現在のルートの終了、<code>archived</code> は資料の収束と保管を示します。</p></div><div><h3>進行中は現在位置も記録する</h3><p><code>active</code> の Study では、01–11 の現在段階、今扱っている作業、次の行動または人の判断も記録します。保留または停止では、理由と再開条件を残します。</p></div><div><h3>状態は人とプロジェクト根拠で確認する</h3><p>テンプレートと validator が確認するのは構造と内部整合性だけです。フォルダを走査して状態を推測せず、段階の正しさ、gate の通過、承認済み判断を証明しません。</p></div></div></section>

<section class="component-section" aria-labelledby="paper-repository-title"><div class="section-header"><div><p class="section-context">v1.18 の追加</p><h2 id="paper-repository-title">一本の論文に対応する公開資料リポジトリを準備する</h2></div><p>原則として、一本の論文または独立して引用できる研究成果に一つのリポジトリを対応させます。まず Study 内で準備し、公開するかは人が決めます。</p></div><div class="boundary-grid"><div><h3>事実に合う公開方式を選ぶ</h3><p>権利とデータ条件に応じて、合成デモ、再配布可能データ、別途のデータ取得手順、または資料のみの package を選びます。公開リポジトリは Study 全体の複製ではなく、実データや実結果を自動で含みません。</p></div><div><h3>allowlist から clean candidate を作る</h3><p>含める資料と除外する資料、コードとデータの権利、実行手順、期待出力、引用情報、版を記録します。候補は新しい clean directory に作り、Study root 自体を Git repository にしません。</p></div><div><h3>検証後も人の承認が必要</h3><p>公開前に、範囲と権利、機微情報、実行可能性、結果対応、独立審査を確認します。System は repository の作成、commit、push、tag、Release を自動実行しません。</p></div></div></section>

<section class="component-section"><div class="section-header"><div><p class="section-context">v1.15 の追加</p><h2>共同審査の順序を記録する</h2></div><p>既定の profile は観察的実証的原著研究向けです。</p></div><div class="boundary-grid"><div><h3>最初に人が profile を選ぶ</h3><p>作業に合う審査 profile を確認します。既定 profile は観察的実証的原著研究だけを対象にします。試験、因果効果研究、予測モデル、系統的レビュー、質的研究、方法論研究などは、別の専門 profile が必要です。</p></div><div><h3>次に審査順序を記録する</h3><p>デザインとガバナンスの事実、データ定義と実行、結果権威、Results、Methods、Discussion、Introduction、要約、投稿資料を審査計画に並べます。後の変更が先に確認した package に影響した時は、再開を記録して再審査します。</p></div><div><h3>管理するのは計画記録だけ</h3><p>v1.15 は空テンプレート、構造検証、再開 metadata だけを提供します。profile を自動選択せず、Study、データ、コード、結果、原稿を読まず、審査通過も決めません。</p></div></div></section>

<section class="component-section"><div class="section-header"><div><p class="section-context">v1.16 の追加</p><h2>原稿要件を Study に入れる方法</h2></div><p>一般的な執筆ルール、研究種別の報告ガイドライン、投稿先ジャーナルの要件を分けて記録し、明示した順序で使います。</p></div><div class="boundary-grid"><div><h3>まず現在の執筆設定を記録する</h3><p>原稿作業では、現在使う要件を <code>09_manuscript/drafting_requirement_stack.yaml</code> に記録します。通常の医学・健康研究では <code>ama_11_default</code> を一般的な出発点にできます。これは公開に確認できる AMA 由来の原則だけを使うもので、完全な AMA Manual の全規則を確認したという主張ではありません。</p></div><div><h3>次に研究種別とジャーナルの要件を加える</h3><p>研究種別に合う報告ガイドラインを加えます。投稿先を決めたら、その時点の著者向け、図表、引用、宣言の要件を加えます。ジャーナル規則が一般執筆 profile と衝突する時は、現在のジャーナル規則を優先します。</p></div><div><h3>衝突は人の判断に戻す</h3><p>ジャーナル要件を使って報告ガイドラインの内容を黙って削除してはいけません。出典、最新性、衝突が不明なら、原稿、図表、引用、宣言を変える前に不足を示し、人の確認を待ちます。</p></div></div></section>
